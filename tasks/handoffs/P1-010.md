## Known risks
- **DISC-P1-010-1 (HIGH, non-blocking): there is no login operation in
  the API at all.** P1-026 built session *verification*; nothing issues
  a session. The httpOnly cookie this task is built around has nothing
  to put in it, so no authenticated screen is reachable by a real human
  through the browser yet — only by tests that mint their own token.
  Recorded rather than papered over with a stub login; it deserves its
  own design (a child has no email or password by contract, so child
  sign-in is a genuinely different problem from parent sign-in).
- Pages for the four parent and two child `primaryNav` screens are
  **shells** — correct route, correct heading, contract-conformant empty
  state, no real data. That is this task's scope ("core navigation and
  API wiring"); content is P1-003/P1-004, live data and recovery states
  are P1-016.
- `C-TASK`, `C-CAMERA`, `SOCIAL-CHAT` have contracts but no pages yet:
  they are not `primaryNav`, and C-CAMERA additionally has no backend
  (DISC-P1-027-1).
- Both apps set `skipLibCheck: true`, scoped to the apps only, not the
  shared base config. Next 16.3's own shipped `.d.ts` references DOM
  types (`URLPatternInput`, `URLPatternOptions`) that TypeScript 5.9's
  lib does not define; this is Next's own `create-next-app` default for
  the same reason. Our code is still fully checked.
- CI now builds two Next apps, which lengthens the `build` step. Worth
  watching if it becomes the slowest gate.

## Decisions
- **Navigation is computed from `SCREENS`, never hand-listed.** A screen
  marked `primaryNav` appears; one that is not does not. A hand-written
  nav array is precisely how a UI drifts from its contract, and ADR-0005
  exists because that drift already happened once with screen ids. A
  test asserts the derived nav equals the contract's own filter.
- **`primaryNavFor` throws on a missing label** rather than rendering a
  blank tab — an unlabelled nav entry should fail loudly at startup, not
  ship as an empty button.
- **State tones are `Record<UiTaskState, _>`**, so adding a state to the
  contract is a compile error here rather than a silent fallback render.
- **The proxy's restrictions are the security posture**, and each is
  tested: allowlisted path prefix (SSRF), no client-supplied headers
  forwarded (token substitution), no redirect following (token leak to
  another origin). There is deliberately **no `getTokenForClient()`** in
  `@life/web-session` — the absence is the feature.
- **Non-`v1` proxy paths are rejected explicitly**, not silently
  rewritten. Slicing the version segment off without checking it would
  have turned `/api/foo/bar` into `/api/v1/bar`.
- **`API_BASE_URL` is not `NEXT_PUBLIC_`** — the browser never calls the
  API directly, so its origin is not the client's business.
- Kept `packages/ui` framework-light (no state library): Server
  Components plus the proxy cover P1-010's needs, and adding
  Redux/TanStack Query before something needs client cache invalidation
  would be speculative.
