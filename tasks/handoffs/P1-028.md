## Known risks
- **DISC-P1-028-1 (MEDIUM, non-blocking)**: `create-child-task` emits a
  task at BACKLOG, but the CLI has no command to walk BACKLOG ->
  ANALYSIS -> ARCHITECTURE_CHECK (`admit` only accepts a PLANNED source).
  A discovery-created task therefore cannot reach READY through the CLI
  at all, forcing exactly the manual `registry.yaml` edit AGENTS.md
  exists to prevent — same class as DISC-P0-003-1. This task's own
  status was moved by hand as a result; disclosed rather than passed off
  as a normal CLI walk.
- The `reject` endpoint's `comment` still has nowhere to persist
  (carried over from P1-026, unchanged here).
- `redeemReward` covers only AVAILABLE -> REDEEMING; the
  REDEEMING -> REDEEMED settlement (`confirmRedemption`) still has no
  exposed operation in the frozen contract. Not in this task's scope —
  the e2e slice's reward assertion goes through task approval's ledger
  grant, which does not need it.

## Decisions
- **`200` for state transitions, `201` for resource creation.** Five
  handlers (publish/start/approve/reject/redeem) were returning NestJS's
  default 201 against a spec that declares 200 — a real defect P1-026
  shipped, surfaced by extending the e2e test through the chain rather
  than by inspection. Fixed at the handler, not by loosening the spec:
  the spec's split is the correct convention.
- `publishTaskTemplate` is idempotent on replay (already-ACTIVE returns
  unchanged, no version bump), matching `startTaskAssignment`'s
  documented repeat-tap rule rather than inventing a new one.
- Rejected auto-publishing on create (recorded in DISC-P1-026-1's
  `alternatives`): DRAFT exists so a parent can build a template before
  children see it (docs/architecture/entity-lifecycle.md); auto-publish
  would silently remove that.
