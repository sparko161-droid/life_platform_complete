## Contracts changed
- **openapi 0.4.0 → 0.5.0.** Both changes *loosen* a request body, so an
  existing client keeps working:
  - `signIn.familyId` optional — the implementation already supported
    bootstrap sessions (DISC-P1-031-1) but the contract still marked the
    field required, so the written contract described a system in which
    onboarding was impossible. `IssuedSession` gains `familyId`, whose
    absence is what routes a client to setup.
  - `createFamily.ownerParentId` optional — vestigial, frozen by P0-009
    before sessions existed. The owner is now always the session actor; a
    *mismatched* value is still refused rather than ignored, so an older
    client fails loudly instead of quietly creating the wrong thing.
- `packages/ux-contracts`: `P-REGISTRATION` and `P-FAMILY-SETUP` moved
  from `SPECIFIED_SCREEN_IDS` to `SCREEN_IDS`.

## Known risks
- **The child surface has no sign-in entry of its own.** A child session
  is provisioned from the parent's device and the resulting id has to
  reach the child's browser; this task delivers the API and the parent
  side, but `apps/child-web` still has no screen that accepts a
  provisioned session. A child cannot yet start using their device
  unattended. Recorded as DISC-P1-032-1 rather than implied by "child
  provisioning" in the task title.
- **`POST /auth/consent` remains unauthenticated** (carried from
  P1-031). The sign-in page's sign-up path shows "accept the terms to
  continue" but there is no consent UI yet, so a new account cannot
  actually finish sign-up through the browser without calling that
  endpoint directly. The API path is complete; the screen is not.
- `createFamily` can be called repeatedly, so one actor can own several
  families, and the session stays bound to the first. That is asserted as
  the safe behaviour rather than left ambiguous, but whether multiple
  families per parent is *wanted* is a product question nobody has
  answered.
- The two frozen screens describe states the pages do not all render yet
  (`LOADING`, `OFFLINE`). The contract is the target; a follow-up should
  check each declared state has a rendering path, which is the check
  P1-016 was scoped to add.

## Decisions
- **The session value never enters a response body.** The route handler
  reads the API response server-side, writes the id into an httpOnly
  cookie, and returns only a redirect target. This is the posture the
  frontend packet confirmed, and it matters most on the child surface,
  which is often a shared device.
- **The web tier does not narrow the API's sign-in failure.** The API
  deliberately returns one undifferentiated failure for wrong password,
  unknown email, suspended account and non-membership; the UI passes it
  through unchanged, because "helpfully" distinguishing them would
  rebuild the account-enumeration oracle in the client.
- **Screens were frozen only once the flows existed.** ADR-0005 requires
  a template-conformant contract before a screen enters `SCREEN_IDS`.
  Writing them now, against real pages, is why they contain concrete
  states rather than plausible-sounding ones.
- **`scopeSessionToFamily` only moves a session out of the unscoped
  state.** It never re-points an already-scoped session, so it cannot be
  used to walk a live session onto another family's data. Asserted by a
  test, because the safe-looking version of this function is the
  dangerous one.
