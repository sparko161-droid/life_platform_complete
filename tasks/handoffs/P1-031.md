## Known risks
- **The screen contracts named in this task's title were not built.**
  The acceptance criteria asked for both API operations *and* a frozen
  contract for the entry screen (`P-FAMILY-SETUP` is in
  `SPECIFIED_SCREEN_IDS` with no contract). Only the API half landed
  here. The screen contract belongs with P1-032, which builds the actual
  sign-in UI and is where a screen contract can be written against
  something real rather than guessed. Flagged rather than quietly
  dropped: this task is DONE against its API scope, not its full title.
- **Throttling is in-memory**, so it does not survive a restart and does
  not coordinate across instances. Honest for Phase 1 (single process),
  and `data-architecture.md` already names Redis for when it stops
  being true. Stated in the module itself, not just here.
- **Consent is recorded, not enforced.** `POST /auth/consent` moves an
  account to ACTIVE, but nothing prevents a `PENDING_VERIFICATION`
  account from signing in — `verifyPassword` accepts both states. That
  matches `family-lifecycle.md` loosely at best; tightening it is a
  product/legal question owned by P1-034, so it was left as-is rather
  than decided here.
- `POST /auth/consent` is unauthenticated and takes an `accountId`. It
  is idempotent and only moves PENDING → ACTIVE, so the exposure is
  limited to an attacker accepting consent on behalf of an account they
  already know the id of — but it should be tied to a session or a
  one-time token before launch. Recorded rather than left unnoticed.

## Decisions
- **The JWT machinery was deleted, not deprecated.** `signSessionToken`,
  `verifySessionToken`, `SESSION_JWT_SECRET` and the `jsonwebtoken`
  dependency had no callers once the guard switched. Keeping a working
  token minter beside a system that no longer trusts minted tokens is an
  invitation to reintroduce exactly the hole this task closed.
- **Throttling keys on email *and* client address.** Per-account-only
  throttling turns lockout into a denial of service: anyone who knows an
  email can burn its budget and lock the owner out. A test asserts the
  owner is unaffected while the attacker's address is blocked.
- **Every failure path is undifferentiated.** Wrong password, unknown
  email, suspended account and non-membership all return the same
  `SIGN_IN_FAILED`; sign-up conflict returns a generic failure. Each
  distinction would be an account-enumeration oracle.
- **Password rule is length-only (10 chars).** Composition rules were
  deliberately not added — they push users toward predictable
  substitutions without adding real entropy.
- **Tests authenticate for real.** `test/helpers/real-session.ts` makes
  every suite obtain a session the way a client does, so the auth path is
  exercised rather than bypassed. This is what surfaced DISC-P1-031-1.
