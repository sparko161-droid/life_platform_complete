## Decisions
- **A session-introspection endpoint rather than a client-readable
  cookie.** This is DISC-P1-003-1 and the one decision here worth
  arguing with. `familyId` decides the security boundary
  (docs/product/actors-and-permissions.md); a second copy of it in a
  place client script can read is a duplicate source of truth that goes
  stale the moment a session is rescoped — which onboarding already does
  (DISC-P1-031-1). One round trip is the smaller cost.
- **The endpoint does not return the session id.** The whole reason the
  web tier stores that value in an httpOnly cookie is that client script
  must not be able to obtain it. A test asserts it never appears in the
  response, because "add sessionId, it's convenient" is exactly the
  change that would pass review.
- **Create → publish → assign stay three calls.** The API models them
  separately on purpose: `createTaskTemplate` returns a DRAFT and
  `assignTask` requires an ACTIVE template (DISC-P1-026-1). Keeping them
  distinct is also what makes a mid-flow failure resumable — `templateId`
  survives a failure, so a retry continues rather than creating a second
  template.
- **Validation is a pure function outside the component.** A rule that
  only exists inside JSX can only be checked by rendering, which makes
  "the wording changed" and "the rule changed" indistinguishable. It is
  also why this task could add tests without standing up a DOM harness.
- **Errors block, warnings do not.** A reward-free task warns; it is not
  refused. A parent may genuinely want one, and refusing would be the app
  overriding them about their own family. A past due date *does* block:
  an assignment that is overdue the moment it appears reads to a child as
  a failure they were never given a chance to avoid.
- **Only three verification strategies are offered.** The contract
  declares ten; CAMERA_EXERCISE, TIMER, COUNTER, ALICE_SESSION and
  COMPOSITE need configuration this screen has no fields for, and
  offering them would create tasks nothing can verify.

## Known risks
- **The screen implements the contract's fields, not the doc's blocks.**
  `docs/ux/screens/parent-task-builder.md` lists ten blocks (schedule,
  prerequisites, progression, notifications, presentation…). The task
  contract has none of them, so the screen covers title, audience,
  verification, reward and due date. The doc and the contract disagree
  about what a task *is*, and that gap is older than this task —
  P1-018's source-of-truth check is where it should be settled.
- **"Preview the exact child experience" is not implemented.** It is in
  the doc's acceptance line but not in the registry's acceptance
  criteria for P1-003. Recorded rather than silently dropped.
- **Editing an existing task is not implemented.** The registry says
  "create/edit/publish"; there is no update operation in the contract at
  all, so edit could not be built without adding one. Create and publish
  are covered.
- **No DOM-level test.** Validation and the session endpoint are tested;
  the rendering path is enforced by the type system via
  `defineScreenStates`, not by a harness that drives the page. P1-011 and
  P1-017 own that.
- **CONFLICT is reachable but untested end to end.** It renders when
  recovery resolves to `REFRESH`; nothing yet forces a real version
  conflict through the UI.
