## Known risks
- **Local Docker Desktop was unreachable in this sandboxed dev
  environment** (`docker info`/`docker ps` hung until timeout after
  repeated attempts, including trying to launch Docker Desktop directly).
  The migration could not be verified against a live database *locally*
  before pushing. To close that gap honestly rather than skip
  verification, CI (`.github/workflows/ci.yml`) now runs a real
  `postgres:17-alpine` service and a migration round-trip step on every
  PR going forward — GitHub's runners have working Docker, so this PR's
  own CI run is the actual first live-DB proof this migration works, not
  a rubber stamp. Recorded here rather than silently assumed to have been
  tested the usual way.
- `verification_results` has no dedicated id in its zod contract
  (`packages/domain-types/src/verification.ts`); the table uses a
  composite primary key `(task_assignment_id, verified_at)` since an
  assignment can be verified more than once across a REJECTED ->
  IN_PROGRESS retry cycle. If two verification attempts for the same
  assignment ever land in the same instant (same `verified_at`), the
  second would violate the PK -- extremely unlikely given ISO-8601
  millisecond timestamps and a human-in-the-loop verification step, but
  worth knowing if P1-025's repository layer ever batches these.
- `parent_memberships` similarly has no dedicated id; `(family_id,
  parent_id)` is its natural key, matching the contract (a parent has
  exactly one membership per family).

## Decisions
- No native Postgres `ENUM` types -- `text` + `CHECK` constraints for
  every status/kind enum, so a new value is a normal `ALTER TABLE ...
  DROP CONSTRAINT / ADD CONSTRAINT`, not `ALTER TYPE ... ADD VALUE`
  (which cannot run inside the same transaction as other DDL in older
  Postgres and cannot be removed once added).
- `reward_ledger_entries.idempotency_key` carries a table-level `UNIQUE`
  constraint -- defense in depth alongside the existing application-layer
  check in `packages/domain-types/src/idempotency.ts`, per
  `docs/architecture/phase-1-scale-guardrails.md` SG-006/SG-007.
- `packages/fixtures/src/domain-generators.ts` generates data by calling
  the real domain-service pure functions (`createFamily`, `addChild`,
  `createTemplate`, `publishTemplate`, `assignTask`), not by hand-building
  objects matching the schema shape -- this means a future domain-service
  behavior change that breaks fixture generation is a real regression
  test failure, not a silent drift.
