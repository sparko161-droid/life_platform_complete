## Known risks
- **Session validation is not yet wired into `SessionGuard`.** The API
  still verifies a signed JWT (`services/api/src/auth/session.ts`).
  ADR-0006 says that becomes a session-record lookup, and this task
  built the lookup — but swapping the guard over belongs with P1-031,
  where the sign-in operations that actually issue these sessions land.
  Until then the sessions table is written and read by tests only, and
  **the revocation guarantee does not yet protect live API traffic**.
  Stated plainly because the opposite reading would be easy.
- No rate limiting or lockout on `verifyPassword`. Argon2id makes each
  attempt expensive, but that is a cost, not a limit.
  `docs/security/threat-model.md` names account takeover as a top
  threat; throttling belongs at the API edge in P1-031 and is not
  silently assumed to be handled here.
- Password reset, MFA and recovery remain out of scope (ADR-0006 D4), so
  a forgotten password is currently unrecoverable by design.
- `@node-rs/argon2` ships prebuilt platform binaries. It resolved and ran
  on both Windows (locally) and will be exercised on linux-x64 in CI;
  worth knowing it is a native dependency rather than pure JS.

## Decisions
- **Argon2 parameters are the library defaults**, deliberately not
  hand-tuned. The stored PHC string carries its own salt and parameters,
  so a future re-tune stays backward compatible with existing rows —
  which is `docs/architecture/versioning-and-compatibility.md` rule 2
  applied to credentials.
- **The parent/child session asymmetry is a CHECK constraint, not only a
  zod rule.** A schema guards what the application writes; a constraint
  guards what the database accepts from a migration, a fix-up script or
  a future service. For "a child can never hold a credential" that is
  worth having twice.
- **Failure paths are undifferentiated on purpose.** Wrong password,
  unknown email and unusable account status all return `null`, and a
  dummy hash is compared on the miss path so timing does not separate
  them. Duplicate registration throws a generic conflict rather than
  "email already registered" — the friendlier message is an account
  enumeration oracle.
- **Email uniqueness is case-insensitive** (`UNIQUE(LOWER(email))`).
  Treating `Parent@x` and `parent@x` as two accounts is a takeover
  foothold, not a feature.
- **`accounts.parent_id` is not a foreign key to `parent_memberships`.**
  `family-lifecycle.md` requires an invitee to authenticate *before*
  membership becomes ACTIVE, so an account must be able to exist with no
  membership row yet. Adding the FK would make the documented flow
  impossible.
- **`revokeParent` cuts sessions in the same transaction** as the
  membership change. A revoked membership with a live session is exactly
  the failure this exists to prevent, so the two must not be separately
  committable.
