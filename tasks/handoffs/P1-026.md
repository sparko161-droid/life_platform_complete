## Known risks
- **DISC-P1-026-1 (HIGH, non-blocking)**: `openapi.yaml` has no
  publish-template operation. `assignTask` requires an `ACTIVE` template
  (task-service.ts), so the frozen HTTP contract cannot reach past
  template creation today -- a client can never assign/start/submit/
  approve/redeem anything through the real API as specified. This
  directly blocks P1-027's E2E acceptance criterion and must be resolved
  before that task can pass.
- The `reject` endpoint accepts a `comment` (required by openapi.yaml)
  but has nowhere to persist it -- no repository writes
  `verification_results` rows at all yet, and `VerifyTaskCommand` has no
  comment field. Accepted, not silently dropped without disclosure, but
  not stored either.
- `start`/`approve` idempotent-replay handling is a pragmatic
  status-check (`if already in that state, return current`) rather than
  a full per-operation idempotency-key ledger like the reward ledger's --
  correct for the documented behavior, but a genuinely malicious/buggy
  client retrying with a *different* body under the same key would not
  be caught as a mismatch (out of scope for this pass).
- Local Docker Desktop was unreachable throughout (same as P1-024/025) --
  every DB-backed test's real pass/fail is CI's job, not this sandbox's.

## Decisions
- `openapi.yaml` already committed to `BearerAuth` (JWT) as the security
  scheme -- `src/auth/session.ts` implements that, not a new choice.
  Claims are `{actorId, role, familyId?}`, matching exactly what
  `services/api/src/repositories/auth.ts` needs.
- `POST /families` accepts `ownerParentId` in the body (the frozen
  contract's shape -- there's no existing membership to check against
  for a brand-new family) but rejects it with 403 unless it equals the
  session's own `actorId`, so self-registration is the only path, never
  creating a family on someone else's behalf.
- `approve` composes `beginVerification -> verifyTask(APPROVED) ->
  completeTask -> grantTaskReward` as one transaction -- the OpenAPI
  summary describes this whole chain ("Emits TASK_APPROVED, then
  REWARD_UNLOCKED once the reward is granted") as one client-visible
  operation, and there is no separate begin-verification endpoint in the
  contract.
