# Handoff — P1-037 Enforce family-scope authorization on every family-scoped endpoint

## Goal
Every family-scoped endpoint refuses a caller whose session is not
scoped to that family, and a test proves each refusal.

## Branch
agent/backend-lead/p1-037-family-scope

## Origin
DISC-P1-004-2, found while writing the family-membership check
DISC-P1-004-1 needed.

## Decisions
- **Not-found and not-yours fail identically.** Otherwise every endpoint
  is an oracle for which ids exist. This is why an unknown assignment id
  now returns 403 where it used to return 404.
- **Resources are located by loading them and checking their
  `familyId`,** never by trusting a family id in the path. A caller
  controls the path; they do not control what the row says.
- **A child must not approve or reject their own work.** Wider than
  "family scope" and called out rather than slipped in. Nothing checked
  it, so a child session could approve its own assignment and be granted
  the reward — the approval step existed but decided nothing. Leaving
  that while doing a security sweep was not defensible.
- **Within a family, a child reaches only their own assignments.**
  Assignments are `CHILD_PRIVATE`; a sibling is inside the family
  boundary but not inside that one.
- **A session scoped to one family does not act on another, even when
  the same parent owns both.** An existing test asserted the opposite.
  ADR-0006 is explicit that authenticating proves who you are, not what
  you may act on — and the comment directly above that assertion already
  said so. The parent signs in again scoped to the other family.
- **Tests are one per endpoint, not a loop.** When one regresses the
  failure should name which door was left open. One test asserts the
  legitimate journey still completes end to end, because a guard that
  refuses everything would pass all the others.
- **`admit` now walks BACKLOG → ANALYSIS → ARCHITECTURE_CHECK → READY.**
  Off-goal for a security task, and included because it blocked creating
  this one. `create-child-task` emits a task at BACKLOG and no verb moved
  it, so every discovery-created task had its status hand-edited — the
  unrecorded state change the lifecycle exists to prevent. Predicted by
  DISC-P1-028-1, recorded again as DISC-P1-036-1, hit a third time here.
  Admission is a single decision that `readyAdmissionProblems` already
  checks; the intermediate states are stages of it, not separate
  approvals, and each step still goes through the same TRANSITIONS
  table.

## Known risks
- **`POST /families` is deliberately unguarded** — it is the one thing a
  bootstrap session may do. A parent can still create unlimited
  families; nothing rate-limits or caps that, and it was true before
  this change.
- **`createFamily` still scopes the caller's session to the new family**
  only when unscoped. A parent who owns two families must sign in again
  to switch, and there is no UI for choosing which family to sign in to.
  That gap is now user-visible in a way it was not before.
- **Authorization is per-endpoint, not structural.** A new controller
  can forget to call the guard and nothing will fail. A route-level
  interceptor or a lint rule would make omission impossible; this change
  makes the rule available and correct, not unforgettable.
- **Capability-level rules are still absent.** `requireParent` is
  role-level; `PARENT_CAPABILITIES` (CHILD_POLICY and the rest) is a
  disclosed placeholder in the contract, so "which parent may do what"
  inside a family is not enforced at all.
- **No test asserts that every route is guarded.** The 14 tests cover
  the endpoints that exist today, enumerated by hand.

## Next tasks
- Make omission structurally impossible (route metadata + a guard, or a
  lint rule that fails an unguarded family-scoped handler).
- Family switching: sign-in scoped to a chosen family, and a UI for it.
- Capability enforcement once `PARENT_CAPABILITIES` stops being a
  placeholder.
