## Known risks
- **"Proof" is a self-report note, not uploaded media.** openapi.yaml
  states the intended reading explicitly ("SubmitProof is the existing
  `submitTaskCompletion` -- TaskCompletion already carries exactly what
  'proof' means (media/counter/timer/note)"), and the test uses
  `selfReportNote` accordingly. But there is still **no media upload
  endpoint anywhere in the contract**, so the PHOTO_PROOF/VIDEO_PROOF/
  AUDIO_PROOF verification strategies cannot be exercised end to end.
  P1-005 built the media domain layer; nothing exposes it over HTTP.
  Recorded as DISC-P1-027-1 — this does not block P1-027's own
  acceptance criterion (which names the journey, not media), but it does
  mean "proof" is currently proven only in its weakest form.
- The rejection comment is asserted to produce a REJECTED state, but the
  comment text itself is still not persisted anywhere (carried over from
  P1-026, unchanged).
- `docker-compose.dev.yml` is named in the task's test strategy as the
  target stack; the tests are stack-agnostic (they use `DATABASE_URL`)
  and in practice run against CI's postgres service, since this
  sandbox's Docker was unreachable throughout. Functionally equivalent —
  same Postgres 17 image — but worth stating plainly rather than
  implying local compose was used.

## Decisions
- **DB assertions bypass the repository layer on purpose.** Reads go
  through a raw pool query rather than `taskRepository.read*`, so a bug
  in the repository cannot mask itself by being both the writer and the
  verifier.
- **"No manual DB intervention" is enforced mechanically**, not
  promised: the suite's `selectRows` helper asserts every statement it
  issues begins with `SELECT`. The test physically cannot seed state
  behind the API's back, so the claim stays true as the file grows.
- **Fixtures supply values, not ids.** Only human-facing fields
  (displayName, birthYear, title, reward amounts) come from
  `generateSyntheticDomainFamilies`; ids are minted by the API, so the
  journey is genuinely HTTP-driven rather than replaying a
  pre-built aggregate.
- Kept this as a **separate suite from http.e2e.test.ts** rather than
  extending it: that one is the API layer's own contract coverage
  (status codes, auth, idempotency), this one is the QA-owned journey
  proof. Different owners, different reasons to change.
