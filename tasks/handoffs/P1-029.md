## Known risks
- **`ChildProfileSchema.birthYear` still accepts 2000–2030**, which
  contradicts the confirmed 4–12 age range (HD-P1-034-1): at a 2026
  reference date the real range is ~2014–2022, and 2030 is a year no
  living child can be born in. Narrowing a frozen contract is a breaking
  change, so it is scheduled on P1-034 rather than done here. Until then
  the schema permits profiles the product does not support.
- **`revokeParent` now has an unmet obligation.** ADR-0006's whole
  justification for session *records* is that
  `docs/product/family-lifecycle.md` promises revocation takes effect
  immediately. The contract makes that expressible; nothing implements
  it until P1-030. The promise is still unmet today — the ADR does not
  change that, it only makes closing it possible.
- **One datastore read per authenticated request** is now baked into the
  design (D2). Accepted knowingly; `packages/scale-guardrails` is where
  it should be measured before anyone optimises it.
- `Account.consentAcceptedAt` carries the consent **flag** only. What is
  consented to, under which rule, is legal work owned by P1-034, and per
  `docs/security/legal-ru.md` nothing here supports a compliance claim.
- The `identity` group's `open_decisions` records that external counsel
  review (HD-P1-033-2) may still change what account or consent data
  must be captured.

## Decisions
All four are recorded properly in **ADR-0006**, with alternatives and a
reversal plan, per `docs/adr/README.md`'s "major security/privacy
decision" trigger. In brief:

- **D1** in-house identity with an `authProvider` seam — so a future
  provider is an additive enum value, not a reshape.
- **D2** server-side session records, not bearer-JWT-only. Follows from
  the revocation promise, which a stateless token cannot honour; the
  cost (a lookup per request) is stated rather than hidden.
- **D3** child access always parent-provisioned. **Derived from the
  frozen contracts, not chosen**: `ChildProfile` has no credential
  fields and `data-architecture.md` requires minimal child PII. Enforced
  by `SessionSchema` itself so it cannot be forgotten by an application
  layer.
- **D4** Argon2id; credential hash on a record separate from the
  aggregate authorization reads; reset/MFA/recovery explicitly out of
  Phase 1 — the same line the API packet drew, kept rather than widened.

Two choices worth calling out beyond the ADR:

- **The rejection messages name the rule.** A child session missing
  `issuedByParentId` fails with "child access is always
  parent-provisioned", and a test asserts the message contains that —
  so the reason survives into whatever surfaces the error.
- **The additive-only claim is enforced, not asserted.** Two guards pin
  the exact field sets of `Family`/`ChildProfile`/`ParentMembership` and
  forbid any pre-existing schema gaining a credential-shaped field —
  which is exactly how someone would later undo ADR-0006 by "just adding
  a password field".
