## Known risks
- **The code is displayed on the parent's screen.** That is the point —
  it is designed to be read aloud — but it does mean a shoulder-surfer in
  the same room could use it. Mitigated by the five-minute window, single
  use, and the fact that redeeming it yields access to one child's own
  data in a family the observer would have to already be standing in. Not
  mitigated at all against someone the parent hands the device to.
  Acceptable for the threat model as written; worth revisiting if pairing
  ever moves off a physically-present flow.
- **Rate limiting does not cover redemption.** `signInThrottle` guards
  sign-in only. An eight-digit code inside a five-minute single-use
  window is a small target, but a determined attacker could try many
  codes against the redeem endpoint. Adding throttling there is a
  genuine follow-up, and the in-memory limitation recorded in P1-031
  applies equally.
- **Sessions are not bound to a device.** A redeemed session works from
  anywhere until it expires or is revoked; pairing controls who *gets*
  one, not where it is then used.
- **No revoke-child-access UI.** `revokeSessionsForChild` exists in the
  repository from P1-030 and nothing calls it. A parent cannot currently
  cut a child device's access from either surface.

## Decisions
- **The pairing artefact is not the session id.** This is the whole
  reason the task exists rather than "show the id". A session id is a
  bearer credential; one read aloud or photographed would defeat the
  httpOnly posture the web tier is built around. A test asserts the two
  are never equal, because the tempting shortcut is exactly the thing
  that breaks it.
- **Redemption is a conditional `UPDATE`, not read-then-write.** Two
  devices racing the same code must not both get a session, and the
  database deciding the winner is the only version of that which is
  actually safe under concurrency.
- **SHA-256 rather than Argon2 for the code.** Deliberate and narrower
  than the credential case: the input has enough entropy for a
  five-minute life and there is no offline-cracking exposure to justify
  a slow KDF on every redemption attempt. Argon2 would be cargo-culting
  the password decision into a different problem.
- **Re-issuing invalidates the outstanding code.** A parent asking for a
  new one has usually lost track of the old one; two live codes is two
  chances for the wrong device to pair.
- **All failures are identical.** Unknown, expired and already-redeemed
  return the same error, so a guessed code cannot be confirmed as real.
- **Child copy tells the child what to do next.** "Код не подошёл.
  Попроси взрослого создать новый" rather than naming a cause — written
  for the 4–12 range confirmed in HD-P1-034-1.
