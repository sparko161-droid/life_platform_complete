# Coverage Audit — discussion to repository

## Purpose
Map discussed product mechanics to authoritative docs and expose gaps before implementation.

## Covered well
- family, parent/child roles, lifecycle and core permissions
- task/verification model, evidence and media
- Task Builder DSL, composite tasks, scenarios and Rules flow
- XP, coins, money ledger, coupons, streaks, levels and skills
- age-aware daily load and child daily loop
- camera pose overlay and deterministic exercise counting
- parent/child/family social graphs and parent social loop
- child messenger, parent chat and protected-read visibility modes
- competition, challenges, moderation, reporting and notifications
- learning sessions, Development Profile and evidence provenance
- AI gateway, knowledge base, avatar and human approval
- Alice, Telegram, MAX and MCP adapter direction
- modular monolith, event model, realtime, storage, device capabilities and CI
- AI team, gates, discovery/rework and phase planning

## Cross-domain links now explicit
- task completion → verification → trusted event → reward/progression
- task builder → scenario/daily load → child day
- parent friendship → case sharing → family relationship
- child friendship → chat → games/challenges
- learning session → evidence → Development Profile → recommendation
- exercise verification → game effect → XP/reward
- integration identity/device → scoped commands/status/notifications

## Remaining design gaps
- executable daily-load calculation and anti-grind policy
- complete reward redemption/expiry/conflict rules
- challenge dispute/cancel settlement
- chat spelling quality scoring and anti-spam model
- exact external account/device linking contracts
- marketplace ranking/abuse prevention
- cooperative game reconnect and session recovery

## Deliberately deferred
- production payment rail
- open child discovery
- public child communities
- full game platform runtime
- advanced AI automatic task verification beyond exercises

## Audit rule
A capability is not considered designed merely because its name exists in the domain map. It needs an owning document, contract, acceptance path and phase/task linkage.
